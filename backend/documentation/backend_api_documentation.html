Interactive, visual reference for the Expense Tracker REST API — a compact Express.js server that manages user transactions, serves financial summaries, and keeps data in sync with a serverless Neon (PostgreSQL) database. Diagrams below are generated from the actual implementation in /backend/src.

1 Backend Overview

The backend is a lightweight RESTful API server that powers the Expense Tracker application. Its single responsibility is to persist and serve user transactions against a serverless PostgreSQL database (Neon). It runs on Node.js with Express 5, uses a lean, layered folder structure (config → middleware → routes → controllers), and delegates heavy lifting to cloud services rather than a large local codebase.

🎯 Main Purpose

  • Store transactions per user (income as positive amounts, expenses as negative).
  • Serve a user's transaction list, newest first.
  • Compute financial summaries: balance, total income, total expenses.
  • Enforce a global API rate limit with Upstash Redis.
  • Expose a health-check endpoint for uptime monitoring.

🏗️ Overall Architecture

  • Monolith, single-process Express app (ES modules).
  • Layered: server → global middleware → routes → controllers → data layer.
  • No service layer — controllers call the SQL driver directly.
  • Serverless data access via Neon's HTTP driver.
  • Cron self-ping keeps the free-hosted instance awake.
Client: The primary consumer is the React Native / Expo mobile app (/mobile). It authenticates users with Clerk on the client side and calls this API with a user_id in the URL/body. The backend itself holds no session state.

3 Request Flow Diagram

How a typical request travels through the backend. This flow is reconstructed directly from server.js, the route definitions, and the controller logic.

sequenceDiagram autonumber participant C as 📱 Client (Mobile app) participant S as Express Server (server.js) participant M as Global Middleware participant R as Routes (/api/transactions) participant K as Controller participant N as Neon PostgreSQL C->>S: HTTP request (GET/POST/DELETE) S->>M: app.use(rateLimiter) M->>M: Upstash sliding-window check (100 req / 60s) alt Rate limit exceeded M-->>C: 429 Too Many Requests else Allowed M->>S: next() end S->>M: app.use(express.json()) M->>S: parsed JSON body S->>M: app.use(cors) M->>R: next() → route handler R->>K: controller function (by route) K->>K: validate inputs (create/delete) K->>N: parameterized SQL (neon driver) N-->>K: rows / result K-->>C: JSON response (200 / 201 / 400 / 404 / 500)

Step-by-step

  1. Client request — The React Native app sends an HTTP request (e.g. GET /api/transactions/:userId) to the Express server.
  2. Express server — server.js receives the request; global middleware runs in registration order.
  3. Rate limiter — rateLimiter.js checks Upstash Redis; if the IP exceeds 100 requests/60s it short-circuits with 429.
  4. Body parser — express.json() parses JSON bodies (for POST).
  5. CORS — Allows cross-origin calls (currently *).
  6. Route — The router matches the path and invokes the matching controller.
  7. Controller — Validates input, then runs parameterized SQL via the Neon driver.
  8. Database — Neon executes the query and returns rows.
  9. Response — The controller sends a JSON response back to the client.

7 Authentication Flow

The backend does not implement authentication. There is no JWT, session, or auth middleware. Identity is established by the React Native client via Clerk and passed to the API as a user_id. The diagram below reflects the real current model — not an invented auth flow.

The mobile app handles sign-in/sign-up with Clerk (email/password, sessions cached in expo-secure-store). Once authenticated, the app knows the user's id and includes it when calling this API. The backend trusts that value as-is.

Implications & authorization model

  • Authorization is "by user_id": each query scopes data with WHERE user_id = ....
  • There is no server-side verification that the caller owns that user_id today.
  • If tighter security is required later, an auth middleware (e.g. verifying a Clerk JWT) could be inserted between Middleware and Routes in the pipeline.

8 Database Layer

Persistence uses Neon (PostgreSQL) through the serverless @neondatabase/serverless driver. db.js exports a single parameterized sql tagged-template client and an initDB() that creates the table if it doesn't exist. All queries are parameterized to prevent SQL injection.

9 Middleware Pipeline

Global middleware is registered in server.js in the exact order below. Each step runs in sequence for every request; the controller/route handlers follow, and error handling is done locally in each controller's try/catch (there is no dedicated error-handling middleware).

flowchart TB IN["📥 Request"] --> A["rateLimiter.js
(Upstash Redis · 100/60s)"] A -->|429 if exceeded| OUT429["❌ 429 Too Many Requests"] A -->|next| B["express.json()
body parser"] B --> C["cors()
origin: *"] C --> D["Routes"] D --> E["Controller"] E --> F["Neon PostgreSQL"] F --> G["📤 JSON Response"] E -->|400 / 404 / 500| G

Interactive walkthrough

1 · rateLimiter.js ▶
Reads req.ip, calls ratelimit.limit(ip) against Upstash Redis (sliding window, 100 requests / 60 s). On failure returns 429; otherwise next(). Config: config/upstash.js.
2 · express.json() ▶
Parses incoming JSON request bodies into req.body (used by createTransaction).
3 · cors() ▶
Enables cross-origin requests; configured with origin: '*' (any origin).
4 · Routes & Controllers ▶
The router matches the path and dispatches to the matching controller function (see section 6).
5 · Error handling (per-controller) ▶
Each controller wraps logic in try/catch. Failures log the error and return 500 {"message":"Internal server error"}. There is no global error-handling middleware.

🗄️ Neon (PostgreSQL)

Primary data store. Accessed only through the serverless neon() HTTP driver with parameterized queries.

🧱 Upstash Redis + Ratelimit

Distributed rate limiting keyed by client IP. No application data is cached in Redis.

🌐 Cron self-ping

node-cron fires every 14 minutes (in production only) and GETs API_URL to prevent the free host from sleeping.
Not present: Cloudinary, Firebase, Stripe, email providers, OAuth, or other third-party REST APIs. The only outbound HTTP caller is the cron self-ping.
